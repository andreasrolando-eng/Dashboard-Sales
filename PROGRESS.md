## Yang Sudah Beres

### 1. Database (semua migration di `supabase/migrations/` sudah di-push)
- Tabel raw: `outlets`, `raw_sales`, `raw_sales_payments`, `raw_sales_menu_items`, `raw_members` (belum dipakai), `sync_log`.
- RLS: tabel raw cuma bisa ditulis service_role; app baca lewat views/functions yang di-grant ke `authenticated`.
- Views agregasi harian: `v_sales_daily_outlet`, `v_sales_hourly_outlet`, `v_sales_product_daily`, `v_promo_daily`, `v_outlets`, `v_categories`, `v_member_visits_daily`, `v_member_branch_counts`, `v_members_dim`, `v_membership_new_weekly`, `v_last_sync`.
- RPC functions: `fn_menu_performance` (FR-21-24), `fn_promo_performance` (FR-25-29), `fn_membership_summary`, `fn_top_members`.

**Keputusan penting soal skema:**
- **`raw_sales_menu_items` primary key = `(sales_num, line_seq)`**, BUKAN `(sales_num, menu_id, batch_id)`. Field `menuID`+`batchID` dari ESB ternyata bisa sama dalam satu transaksi (dikonfirmasi user), jadi satu-satunya ID yang reliable dari ESB cuma `salesNum` di level bill. `line_seq` adalah nomor urut posisi item di array `salesMenus[]`, di-generate sendiri oleh ETL (migration `20260813100000`, ada `truncate` karena PK berubah total — semua data menu item lama perlu di-sync ulang).
- **Nett Sales**: kolom `nett_sales` di `v_sales_daily_outlet` dan `v_sales_daily_outlet_category`. Formula **terbaru** (migration `20260821100000_nett_sales_formula_revision.sql`, **sudah di-push**, keputusan bisnis dari user — basis sengaja diganti dari `grand_total` ke `subtotal`, dan deduction dipangkas jadi cuma 3 komponen):
  ```
  nett_sales = subtotal
             - (other_tax_total + vat_total + other_vat_total)
             - discount_total
             - rounding_total
  ```
  `voucher_discount_total`, `order_fee` (platform fee), dan `delivery_cost` **sudah TIDAK dikurangkan lagi** — beda dari versi sebelumnya. Riwayat: formula pertama kali ditambahin migration `20260813100100`+`20260813100200` (basis `grand_total`, 6 komponen deduction, termasuk platform fee/delivery); versi itu juga dipakai buat alokasi proporsional `nett_sales` per kategori di `v_sales_daily_outlet_category` (migration `20260820090000`). Migration `20260821100000` update FORMULA-nya doang di kedua view itu (`create or replace view`, nama/urutan kolom gak berubah) — mekanisme alokasi proporsional per kategori di `v_sales_daily_outlet_category` (nett_ratio per transaksi × porsi item) tetap sama persis, cuma rumus `tx_nett` di dalamnya yang diupdate.
- **Filter kategori menu keyed by `menuCategoryID`, bukan `menuCategoryName`** (migration `20260814090000_category_filter_by_id.sql`, **sudah di-push ke database live**). Nama kategori dari ESB gak dijamin stabil ejaannya antar sync (ID yang sama bisa muncul lagi dengan nama beda), jadi filter text-equality by nama itu rapuh — sama alasannya kayak keputusan PK `raw_sales_menu_items` di atas. `v_sales_product_daily` sekarang punya kolom `category_id` (key) + `category` (nama, buat display doang). `v_categories` jadi satu baris per `category_id`, dengan `category_name` = nama paling sering muncul (`mode()`) buat ID itu. `fn_menu_performance` filter pakai param `p_category_id`. Dropdown kategori di `filter-bar.tsx` sekarang `value={category_id}` / label `{category_name}`.
  - **Gotcha migration yang kejadian pas nge-push** (kalau nanti ganti kolom/param lagi, inget ini): `create or replace view` **gak bisa** insert kolom di tengah / rename kolom existing (cuma boleh nambah kolom baru di paling akhir) → harus `drop view ... cascade` + `create view` ulang. `create or replace function` juga **gak bisa** rename parameter maupun nambah/ubah kolom return table (`SQLSTATE 42P13` / cannot change return type) → harus `drop function` + `create function` ulang juga. Drop otomatis buang privilege yang udah di-grant, jadi abis drop+recreate wajib `grant select`/`grant execute ... to authenticated` ulang di migration yang sama.
- **Filter kategori detail menu keyed by `menuCategoryDetailID`** (migration `20260814100000_category_detail_filter.sql`, **sudah di-push**) — level kedua di bawah kategori (1 menu = 1 kategori + 1 kategori detail, misal kategori "Makanans" detail "Nasi Goreng"). `v_sales_product_daily` nambah 2 kolom di paling akhir (`category_detail_id`, `category_detail`) via `create or replace view` biasa (aman karena nambah di akhir, bukan di tengah). View baru `v_category_details` (sama pola kayak `v_categories`, `category_detail_name` = `mode()`). `fn_menu_performance` di-drop+recreate lagi dengan param baru `p_category_detail_id` + kolom return `category_detail`. Dropdown kategori-detail baru ditambahin di `filter-bar.tsx` (sejajar sama dropdown kategori), state-nya di `useDashboardFilters` (`categoryDetail`, sentinel `ALL_CATEGORY_DETAILS`). **Scope-nya sama kayak kategori** — tetap cuma dari transaksi `status_name = 'Finished'` (user pilih ini pas ditanya, bukan expand ke semua raw data).
- **FYI soal `status_name = 'Finished'` filter**: `v_categories`/`v_category_details` cuma nampilin kategori/detail yang PERNAH muncul di transaksi Finished. Kalau ada kategori baru di ESB yang transaksinya masih New/Cancelled/Void, dia gak akan muncul di dropdown sampai ada transaksi Finished pertama di kategori itu — ini disengaja/konsisten sama semua angka lain di dashboard, bukan bug.
- **Nama kategori/kategori-detail di dropdown sekarang dari raw data langsung, bukan `mode()`** (migration `20260814110000_category_name_from_raw.sql`, **sudah di-push**). Awalnya `v_categories.category_name`/`v_category_details.category_detail_name` dihitung pakai `mode()` ("nama paling sering muncul") buat 1 `category_id` — itu tetap salah satu nilai raw asli, tapi hasil pilihan statistik, bukan raw record tertentu. Sekarang pakai `distinct on (category_id) ... order by category_id, sales_date desc` — ambil nama dari baris `raw_sales_menu_items` dengan `sales_date` PALING BARU buat ID itu, jadi kalau kategori pernah di-rename di ESB, dropdown nampilin nama TERKINI. Bentuk kolom view gak berubah, jadi gak ada perubahan frontend sama sekali di sini.
- **Hierarki category > category detail > menu, sekarang beneran di-enforce** (migration `20260814120000_category_detail_hierarchy.sql`, **sudah di-push**). Dikonfirmasi dari data live: tiap `category_detail_id` cuma pernah nempel ke SATU `category_id` (mis. "Nasi Goreng" selalu di bawah "Makanans"). Sebelumnya `v_category_details` flat — gak nyimpen parent `category_id`-nya — jadi dropdown detail nampilin semua detail sekaligus tanpa peduli kategori yang lagi aktif. Sekarang `v_category_details` punya kolom `category_id` (kolom baru di paling akhir, `create or replace view` aman). Di `filter-bar.tsx`, dropdown kategori-detail otomatis ke-filter cuma nampilin detail yang parent-nya = kategori yang lagi dipilih (`categoryDetailOptions`), dan kalau ganti kategori sementara detail yang lagi kepilih gak lagi valid di kategori baru, otomatis di-reset ke "Semua Kategori Detail" (`setCategoryAndDetail` di `useDashboardFilters` — dipakai biar category+categoryDetail keupdate di URL dalam satu `router.replace`, soalnya 2 `update()` terpisah di handler yang sama bakal race/saling timpa gara-gara sama-sama baca `searchParams` yang masih stale).

### 2. ETL — Edge Function `sync-esb` (sudah deployed)
- **Request contract terkonfirmasi** (bukan tebakan lagi):
  - Endpoint: `{ESB_API_BASE_URL}/corev1/sales/sales-information`
  - Auth: `Authorization: Bearer <token>`
  - Query params: `salesDateFrom`, `salesDateTo` (yyyy-mm-dd), `page` (default 1), `sortBy=salesDateIn`, `sortOrder=asc`. **Tidak ada param `perPage`** — page size fixed 20 di server (dari `x-pagination-*` response headers).
  - Sengaja **tidak** filter `statusName` (ambil semua: New/Finished/Cancelled/Void) — biar raw data lengkap buat audit. Filter "Finished" dilakukan di SQL views, bukan di request.
  - Sengaja **tidak** filter `branchCode` — ambil semua outlet dalam 1x request per tanggal, lebih efisien daripada loop per outlet.
- Idempotent: upsert berbasis `sales_num` (dan `sales_num+line_seq` untuk item menu, `sales_num+sales_payment_backend_id` untuk payment) — sync ulang tanggal yang sama aman, tidak dobel.
- Mendukung **sync 1 hari atau rentang tanggal** (`{date}` atau `{dateFrom, dateTo}`), maks 31 hari/request, tiap hari punya baris `sync_log` sendiri (kalau 1 hari di tengah gagal, hari lain tetap sukses).
- CORS sudah di-enable (`supabase/functions/_shared/cors.ts`) — bisa dipanggil langsung dari browser.
- Monitoring: ping ke `HEALTHCHECKS_PING_URL` (sukses/gagal) kalau di-set.
- **Sinkronisasi manual dari dashboard**: tombol "Sync Manual" di header (semua tab), dengan date-range picker. Kalau ada hari yang gagal, muncul chip merah per tanggal buat retry cuma hari itu.

Ini lossless kalau dijumlah balik semua kategori (hasilnya = `nett_sales` transaksi asli persis), sudah diverifikasi lewat mock (`mockSalesDailyOutletCategory` di `src/lib/mock/queries.ts`).

Ini disengaja: angka default "Semua Kategori" gak boleh berubah sama sekali (sum item-level gak dijamin sama persis ke rupiah dengan sum `grand_total`), jadi cuma numbers pas filter aktif yang beda basis perhitungannya.
  - KPI lain di tab Sales (Total Transaksi, AOV, Peak Hour) **tetap gak ke-filter kategori** — sengaja, biar AOV gak nyampur revenue-yang-difilter dengan trans_count-yang-gak-difilter (bakal jadi angka yang gak masuk akal).
- **Panel "List Transaksi"** (tab Sales, di bawah Menu Underperforming, migration `20260821090000_sales_bills_list.sql`) — drill-down 1 baris per bill (`bill_num`, tanggal, outlet, total), scope cuma `status_name = 'Finished'` (sama kayak semua angka lain). View baru `v_sales_bills` sumber langsung dari `raw_sales` (bukan tabel agregat).
  - Urutan `sales_date asc, bill_num asc` — **bukan** urut murni by `bill_num`, karena formatnya `{OUTLET}{YYYYMMDD}{urutan}` (mis. `SMOLT202608180002`) jadi urut string apa adanya bakal ngelompok per outlet dulu (semua bill SMOLT, baru TAOUT, dst), bukan kronologis, pas outlet-nya "Semua Outlet".
  - **Beneran di-paginate server-side** (`getSalesBills` di `src/lib/queries/sales.ts`, pakai `.range()` + `count: "exact"`), bukan "tampilkan N teratas" kayak panel lain — 1 bulan buat "Semua Outlet" bisa ribuan baris, jauh di atas `max_rows: 1000` PostgREST.
  - Komponen `sales-bill-list-panel.tsx` di-remount pakai `key={outlet|dateStart|dateEnd}` dari parent tiap filter ganti, biar `page` balik ke 1 tanpa perlu `useEffect` + `setState` (itu kena lint error `react-hooks/set-state-in-effect` — cascading render).
  - **Gotcha TypeScript yang kejadian pas nulis `getSalesBills`**: nge-`.map()` inline buat convert `grand_total: number | null` → `number` LANGSUNG di dalam `return` (yang posisinya kena contextual typing dari signature `Promise<{rows: SalesBill[]...}>`) bikin `data` ke-infer jadi `never` (`tsc` error "Spread types may only be created from object types"), padahal query-nya sendiri valid (kebukti kalau cuma `console.log(data)` gak ada error). Fix-nya: pindahin `.map()` ke helper function terpisah yang punya parameter type eksplisit sendiri (`toSalesBills(rows: {...}[])`), sama pola kayak `sumCategoryRevenue` yang udah ada duluan.
